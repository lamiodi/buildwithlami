# Buildwith_lami — Authentication Model

This document is the **single source of truth** for how authentication
and authorization work across the Buildwith_lami stack. It was written
during the production-readiness remediation (see
`PRODUCTION_READINESS_AUDIT.md`) to make the model explicit and to
prevent two contradictory auth schemes (cookie + JWT + CSRF token)
from re-appearing in the codebase.

---

## TL;DR

| Surface         | Credential (authoritative)        | Helper (same-origin only)        |
| --------------- | --------------------------------- | -------------------------------- |
| **Admin app**   | `Authorization: Bearer <token>`   | `access_token` HttpOnly cookie   |
| **Client app**  | `Authorization: Bearer <token>`   | `client_token` HttpOnly cookie   |
| **Public APIs** | URL token, public rate limit only | n/a                              |

* **No CSRF token system.** The cookies are `SameSite=Strict`, so a
  third-party site cannot ride them. The `Authorization` header is
  never auto-attached by the browser, so it cannot be replayed
  cross-origin either. Belt and braces, modern-style.
* **No session storage server-side.** All session state is inside the
  signed JWT. Revocation is by changing `JWT_SECRET` / `CLIENT_JWT_SECRET`.
* **Two secrets, never one.** Admin tokens are signed with
  `JWT_SECRET`; client tokens with `CLIENT_JWT_SECRET`. A stolen
  client token cannot be replayed against admin routes, and vice
  versa.

## 1. Admin authentication

### Where the token lives

1. `localStorage.admin_token` — set by `AuthContext.login()` /
   `AuthContext.extendSession()` after a successful
   `POST /api/auth/login` (or `/api/auth/login/2fa` /
   `POST /api/auth/refresh`).
2. `access_token` HttpOnly cookie — set by the backend on the same
   responses. Read by the middleware as a fallback.

### How requests authenticate

The frontend API client
(`frontend/src/services/api.js`) reads the token from
`localStorage.admin_token` and attaches it as
`Authorization: Bearer <token>`. This is the **authoritative**
credential.

The `access_token` cookie is a convenience for direct browser
navigation (e.g. pasting a deep link into a new tab). The backend
middleware reads `Authorization` first, then falls back to the
cookie.

### Token shape

* Algorithm: HS256.
* Payload: `{ id, email, role, iat, exp }`.
* Lifetime: 30 minutes (sliding — `POST /api/auth/refresh` resets the
  window).
* Secret: `process.env.JWT_SECRET`.

### Roles

* `Owner` — the only admin role in the one-man studio
  (post `v38_simplify_roles.sql`). Every admin-only route is
  gated by `requireRole('Owner')` (see
  `backend/src/middlewares/authMiddleware.js`).

### Why no CSRF

* The `access_token` cookie is `SameSite=Strict`, so a third-party
  site cannot ride it.
* The `Authorization` header is never auto-attached by the browser
  on cross-origin requests, so even if a third-party site could
  reach our backend, it would not have the token to send.
* The CORS allowlist blocks `credentials: 'include'` from any
  origin we do not trust.

We removed `csurf` because it added a second, parallel auth model
that was not actually defending anything (the cookie is HttpOnly
and SameSite=Strict, so the JS-side `X-CSRF-Token` header was
never going to be replayed by a third party).

## 2. Client authentication

### Where the token lives

1. `localStorage.client_token` — set by
   `ClientAuthContext.login()` after `POST /api/client-auth/login`.
2. `client_token` HttpOnly cookie — same response.

### How requests authenticate

`frontend/src/services/api.js` is called with `auth: 'client'`
for every authenticated client-portal call. The helper then reads
`localStorage.client_token` and sends `Authorization: Bearer
<token>`. The `client_token` cookie is a fallback for direct
browser navigation.

### Token shape

* Algorithm: HS256.
* Payload: `{ id, email, role: 'CLIENT_PORTAL', iat, exp }`.
* Lifetime: 24 hours.
* Secret: `process.env.CLIENT_JWT_SECRET` (falls back to
  `JWT_SECRET` in dev, with a warning in production).

### Role

* `CLIENT_PORTAL` — only role. Verified by
  `verifyClientToken` in
  `backend/src/middlewares/clientAuthMiddleware.js`.

### Why no CSRF

Same reasoning as the admin side. The cookie is HttpOnly +
SameSite=Strict, and the client SPA is served same-origin.

## 3. Tracking-page authentication (no login)

The public project tracking page
(`/track/:trackingId`) uses a separate, scoped auth mechanism:

* `trackingId` in the URL is the project identifier.
* Sensitive actions (reveal secrets, submit feedback, accept a
  milestone) require a one-time, single-use URL token generated by
  the admin and shared out-of-band (email). The token is verified
  server-side and is rate-limited per IP.

This is a **third auth model** that lives only inside the public
tracking surface. It does not share storage with the admin or
client auth flows.

## 4. Webhooks (no auth, signature-only)

Public webhook endpoints validate authenticity via HMAC
signatures, not JWTs:

* **Paystack**: `X-Paystack-Signature` header, HMAC-SHA512 of the
  raw body, compared with `crypto.timingSafeEqual`. See
  `backend/src/controllers/paymentController.js`.
* **Zoho Sign**: `X-Zoho-Signature` header, HMAC-SHA256 of the raw
  body, with optional `X-Zoho-Timestamp` for replay protection.
  In stub mode the same path is gated by a dedicated
  `STUB_WEBHOOK_SECRET`. See
  `backend/src/utils/webhookVerify.js` and
  `backend/src/controllers/contractController.js`.

Webhook routes are explicitly skipped by the general API rate
limiter (see `apiLimiter.skip` in `backend/src/index.js`) so a
burst of legitimate deliveries cannot exhaust the public API
rate-limit window for real API consumers.

## 5. CORS

* `backend/src/index.js` configures `cors({ origin: allowedOrigins,
  credentials: true })`.
* `allowedOrigins` is the `FRONTEND_URL` env var plus the canonical
  production domains and `http://localhost:3000` for dev.
* `credentials: true` is required because the cookie fallback is in
  play; in a strict same-origin production setup the cookie is
  first-party and never crosses origins.

If you ever split the frontend onto a different origin than the
backend, the cookie flow breaks. The Bearer header keeps working,
so the SPA should always be able to authenticate even when the
cookie fails. The CORS allowlist should be tightened in that case.

---

## 6. Production deployment assumptions

* `NODE_ENV=production` so the cookies get `secure: true` (HTTPS only).
* `JWT_SECRET` and `CLIENT_JWT_SECRET` are unique, high-entropy
  values, never shared.
* `TWOFA_ENCRYPTION_KEY` is set so TOTP secrets are encrypted at
  rest (see `backend/src/utils/twoFactorCrypto.js`).
* `ZOHO_SIGN_WEBHOOK_SECRET` (or `STUB_WEBHOOK_SECRET` in stub
  mode) is set so the Zoho webhook cannot be silently signed by an
  unauthenticated request.
* `PAYSTACK_SECRET_KEY` is set so the Paystack webhook signature
  is verified.

---

## 7. What is NOT in scope (intentionally)

* Refresh-token rotation — not needed at this scale; the 30-minute
  sliding window with `/auth/refresh` is sufficient.
* Server-side session store — the JWT is the session.
* Multi-role RBAC — Buildwith_lami is a one-man studio; the only
  admin role is `Owner`.
* Account-level "logout everywhere" — rotating `JWT_SECRET` is the
  blunt instrument. Not currently exposed in the UI.
