## 2. Workflow map (as actually implemented)

**Roles:** exactly one admin identity (`Owner`, admin JWT via `/api/auth/login`, 2FA optional, lockout after repeated failures) and two client token families:
- **Tracking-link client** (`role:'Client'`, 7-day JWT signed with `JWT_SECRET`) — minted by `POST /api/client-projects/track/:trackingId/auth` (knowing the 32-hex tracking ID + matching client email; anti-enumeration 401s) or the admin magic link. Powers `/track/:id` pages.
- **Portal client** (`role:'CLIENT_PORTAL'`, 24h JWT signed with `CLIENT_JWT_SECRET`) — email + bcrypt password at `/portal/login`. Powers `/portal/*`.

**Client journey and status transitions:**

| Stage | Actor | Prerequisite | DB effect | Notification |
|---|---|---|---|---|
| Enquiry | Public | — | `messages` row + auto `leads` row (`LEAD`, source `contact_form`/`booking_form`) with service/tier/currency | admin email |

## 3. Findings

Severity = client impact if unfixed. "Fixed (source)" = change is in the working tree, **not** deployed.

### CRITICAL

**C1 — Production payment dead-end: no working payment method for clients.**
- Evidence (live): `POST /api/invoices/webhook/paystack` returns `500 {"error":"Webhook not configured."}` for any payload → `PAYSTACK_SECRET_KEY` is unset on Render; `GET /api/payments/bank-accounts` (admin) shows **0 of 2 bank accounts active**.
- Impact: NGN invoices get no Paystack link; USD/GBP clients get an empty bank list. A client with an invoice today cannot pay at all, and even if Paystack were configured without the key the webhook could never verify payments.
- Fix: **ops action, not code** — set the Paystack secret key on Render and activate a real bank account. (Code fix for webhook guards in M1 below is also in this tree.)

**C2 — Cross-client invoice exposure (access control).**
- `GET /api/invoices/project/:projectId` (`invoiceRoutes.js:27`) admits client-role tokens but queried `WHERE project_id = $1` with **no tenant filter**. A client holding a legitimate tracking-link token could read every invoice of any project UUID — amounts, statuses, `pay_token` (which itself unlocks the public payment page + proof upload for that invoice), and payment references.
- Evidence: E2E repro on the isolated stack — client A's token fetched client B's full invoice rows incl. `pay_token`. Live today: not exploitable (0 clients exist) but Critical the first day two clients coexist.
- **Fixed (source):** query joins `client_projects` and filters by the token's `trackingId`; owner path unchanged. Regression test R1.

### HIGH

**H1 — Executed contract document downloadable with no credentials.**
- `GET /api/contracts/:id/pdf` was registered **before** the auth middlewares (`contractRoutes.js`) — anyone with a contract UUID (exposed in portal responses, emails, logs) got the full contract: terms, amounts, signer email, signature image, signer IP, audit hash.
- Evidence: isolated-stack repro returned full HTML anonymously; live probe on a random UUID returns 404 (not 401), proving no auth runs on the deployed route.
- **Fixed (source):** route now requires the Owner token **or** the contract's signing token (`?token=…`); malformed UUIDs are 400 not 500. Portal "Download PDF" link updated to present the signing token. Regression test R2.

**H2 — Admin Tasks page dead on production (500 on every load).**
- `GET /api/tasks` 500s on live: `ORDER BY t.priority_rank` treats a SELECT alias as a column (`column t.priority_rank does not exist`). Every AdminTasks / Tonight-Queue list call failed.
- Evidence: live `GET /api/tasks` → 500; fixed SQL verified against the live schema (runs clean).
- **Fixed (source):** unqualified `ORDER BY priority_rank`. Regression test R3.

**H3 — Admin Settings → Profile broken on production (500).**
- `profileController` queried `WHERE id = 1` but `profile.id` is a **UUID** (and the table is empty). Both read and write always threw `uuid = integer`.
- Evidence: live `GET /api/profile` → 500; live schema probe confirms `id:uuid`, 0 rows.
- **Fixed (source):** singleton resolved by `ORDER BY updated_at LIMIT 1`; insert lets the DB default generate the UUID. SQL verified against live. Regression test R4.

**H4 — Owner session lasts 7 days and cannot be revoked.**
- Live login minted a token with `exp−iat = 10080 min` (Render `JWT_EXPIRES_IN`), vs. the documented 30-minute sliding session with refresh. There is no token blacklist anywhere; logout only clears the cookie; password reset does not revoke outstanding JWTs. A leaked admin token is valid for a week.
- Fix: set `JWT_EXPIRES_IN=30m` on Render (the frontend refresh flow already handles renewal). **Not changed** (env decision).

**H5 — 2FA is disabled on the live owner account.**
- Live login returns a token with no 2FA challenge, contradicting the RBAC doc ("2FA is mandatory for the owner"). Combined with H4 this is the whole admin attack surface.
- Fix: enable via `/admin/security/2fa`. **Owner action.**

### MEDIUM (all fixed in source unless noted)

- **M1 — Webhook money-integrity guards** (`invoiceController.paystackWebhook`): the old guard `status <> 'PAID'` let a replayed/out-of-order `charge.success` flip a REFUNDED/CANCELLED invoice back to PAID; amount mismatch was a silent 200 (Paystack never retries → lost payment, no reconciliation signal); currency never checked. **Fixed:** only `PENDING/OVERDUE/PARTIAL` flip; mismatches and unknown references log loudly for reconciliation.
- **M2 — Payment-proof review guards** (`paymentController.reviewProof`): no `status='PENDING'` guard (a REJECTED proof could be confirmed after the fact), no `status<>'PAID'` guard on the invoice flip, and the claimed amount was never compared to the invoice. **Fixed:** atomic status-guarded updates (racing/double reviews → 409), amount equality within 0.01 enforced, invoice only flips from payable states.
- **M3 — Quotation status machine unvalidated** (`quotationController`): any transition was allowed (e.g. CONVERTED→DRAFT), conversion had a double-convert race creating duplicate contracts, and converted contracts dropped the quotation's currency (USD quote → NGN contract). **Fixed:** explicit transition map enforced atomically in SQL, conversion runs in a transaction with `FOR UPDATE` + status-guarded flip, currency/amount/title carried into the contract.
- **M4 — Public booking API accepted past dates** (live-confirmed: `preferred_date=2020-01-01` → 201). **Fixed:** server-side "not in the past" validation (frontend already validated).
- **M5 — Portal login label misleading:** "Password (or Tracking ID)" — the backend is email+bcrypt only, so following the label locks clients out at the front door. **Fixed:** label now "Password".
- **M6 — `/track` with a bad link showed a bare "Request failed"** — a screen with no next step for a client. **Fixed:** friendly error card with "Contact us" / "Back to homepage".
- **M7 — Onboarding autosave race (data loss):** `saveMyOnboarding` took a `FOR UPDATE` lock **outside any transaction** (released immediately), so two concurrently autosaved sections could merge against the same snapshot and lose one section's answers. **Fixed:** read-merge-write wrapped in a real transaction.
- **M8 — Invoice email always had blank client/project names** (`createInvoice` selected neither column). **Fixed:** both selected and passed to the email.
- **M9 — Refund leaves inconsistent records** (`PATCH /invoices/:id/refund` clears `paid_at` but leaves the receipt standing and never re-derives the project's `payment_status`). **NOT fixed — needs a business decision:** should a refund void the numbered receipt (delete) or keep it with a note? Paystack-initiated refunds aren't called either. Tell me the intended policy and I'll implement.

### LOW

- **L1 — Login error UX:** any admin login failure showed the generic "Request failed" (HTTP/2 has no statusText and `api.js` ignored string-valued `error` fields). **Fixed** in `api.js` — backend messages like "Invalid credentials." now surface verbatim app-wide.
- **L2 — Fresh-install DB chain was broken three ways:** `runInit.js` never ran `createMissingTables.sql` (migrations then crash at v5), v47's guarded `tasks` drop crashed on any DB where `tasks` never existed (PL/pgSQL plans the `COUNT(*)` eagerly), and v42+ need pgcrypto (Supabase ships it; vanilla Postgres doesn't). **All fixed** (v47 rewritten with dynamic probes, pgcrypto ensured in v42, `db:init` now applies both baseline files). Matters for disaster recovery: a fresh Supabase project could not previously be rebuilt from the repo.
- **L3 — No server-side dedupe on contact submissions** (UI double-click guards exist; two identical POSTs both store). Report only — needs a policy (idempotency key vs. acceptance).
- **L4 — Header logo/wordmark overlap** (cosmetic, desktop + mobile). Report only.
- **L5 — Portal `GET /contracts` returns `SELECT c.*`** including `signing_token` + `audit_trail`. The token is needed for the (now token-gated) PDF link; consider trimming `audit_trail` later.
- **L6 — Contract integrity hash binds only the first 50 chars** of the drawn signature (`contractService.computeContractHash`). Tamper-evidence is weaker than the UI implies. Design decision.
- **L7 — Contract signing never verifies the signer's email** against `signatory_email` — the 256-bit token is the only identity proof (reasonable for a one-man studio; document it).
- **L8 — Client portal login has no lockout** and sits behind the generic 100/15-min limiter (admins get 20/15 + lockout). Consider `authLimiter` + client lockout counters.
- **L9 — `/login` Enter key doesn't submit** (button click works; `requestSubmit` works). Minor a11y annoyance; needs a small repro to root-cause.
- **L10 — `onInvoicePaid` re-runs reset `next_action_due_at` every time** (not gated on first-run). Cosmetic automation quirk; report only.

### Workflow gaps (missing features — reported, not invented)

- **Portal "Messages" page is simulated** — it `setTimeout`s and never calls the API. Clients believe they sent a message; nothing is stored and the admin is never notified. Biggest honesty gap in the portal; recommend either wiring it to a real endpoint or removing the page.
- Public quote-acceptance link was deliberately deferred — acceptance is admin-recorded (consistent with design).
- No reconciliation cron for missed webhooks (while Paystack is unconfigured, this matters doubly — admin must confirm payments manually).
- No contract versioning/supersede flow (quotation versioning exists; contracts are single-row).
- Closed/archived projects have no self-serve "reopen" — status changes are admin-manual (acceptable for a one-man studio; listed for completeness).
- Stripe: not integrated (unused column + UI mention only). USD/EUR/GBP are bank-transfer-only by design.
